# Package compatibility

Current importer manifest version: 0.2.1. Locally tested wire package version: 2. The committed `contracts/import-sync/` directory is a snapshot of the producer contract, not a runtime dependency on a sibling checkout. `fixtures/compatibility/contract-snapshot.json` and `managed-snapshot.json` record each schema hash and the Bridge version used for the fixture set.

| Fixture | Produced by | Class stable keys | Checked here |
| --- | --- | --- | --- |
| `image.json`, `ui-kit.json`, `page.json` | Bridge 0.2.0-alpha.1 legacy `compile` | `<componentKey>/class/<name>` | image bytes verified; page roles unchanged after the kit |
| `managed-ui-kit.json`, `managed-page.json` | Bridge 0.2.0-alpha.1 managed `build` (2026-10-09), via the Bridge script `system/scripts/export-compatibility-fixtures.js` | `<namespace>/class/<name>`, shared by kit and page | both packages inspect; page with one embedded image; UI-kit roles unchanged, no conflicts |

Class stable keys are opaque to the importer. Receipts remain keyed by target, namespace and component key, so a page import still adopts identical UI-kit classes by name and never rewrites them.

These tests establish local compatibility for those cases only. A clean editor import, save/reload, older Bridge versions, future package rejection and Chrome Web Store installation still require separate evidence before the public compatibility table is expanded.

To refresh the managed fixtures, run the Bridge script into a new directory, review the diff, then copy the three `managed-*` files here in one change together with any contract update.

## Editor facts the importer relies on

| Fact (how and when verified) | Importer rule |
| --- | --- |
| Taptop keeps all classes of a site as one selector collection with `selectorCollectionDataVersion` (an integer) and `selectorCollectionSchemeVersion` in the editor state store (module 87621, with `savingState`). Every save uploads the whole collection with the tab's version and receives the next one; a tab older than the server answers code `11` "wrong version", and the «Сохранить мой дизайн» choice re-saves with `force`, overwriting newer styles. Live, two tabs of a disposable site, 2026-11-26 | The importer never sends a version and never saves. A first 0.2.1 build compared the tab's version with the server's (`getSelectorCollection`); the Taptop developers asked not to request the collection (2026-11-27), so 0.2.1 reads only `savingState`: before images are uploaded and right before the first class write or paste it waits up to 15 s while a save runs (`EDITOR_SAVE_PENDING`) and refuses after a failed save (`EDITOR_SAVE_FAILED`); an editor whose store it cannot find is not refused. Class writes also re-read the planned classes; a difference is logged to the console (`classes read differently than when the import was planned`) and does not stop the import. Tests: `test/save-state.test.js` |
| Module ids change when Taptop rebuilds the editor: the layer clipboard (`pasteFromClipboard(marker, rootId)`, with `getClipboard`/`clearClipboard`) moved from 6269/13339 to 48511, and 0.2.0 then failed every import with «Редактор Taptop не ответил» (`EDITOR_UNAVAILABLE`, reported by a client 2026-11-26; module read live the same day). The animation clipboard (65821) also has a `pasteFromClipboard`. The rspack runtime exposes module definitions (`require.m`) but no cache (`require.c`) | 0.2.1 tries 48511 first, then scans module sources for `static pasteFromClipboard(` and takes only an export without `setAttrAnimation`. Test: `test/taptop-runtime-adapter.test.js` |
| The editor of a site with a connected domain opens at `https://<domain>/-/cms/v1/mosaic/…`, not on `*.taptop.site`; 0.2.0 matched only `*.taptop.site`, so the launcher and the popup stayed silent there (reported by a client, 2026-11-26) | 0.2.1 matches the editor path on every https host (`host_permissions` and the content script: `https://*/-/cms/v1/mosaic/*`), so the launcher appears by itself on a connected domain too. A first attempt that asked for each domain from the popup was dropped the same day: a tester expected the button and never opened the popup. Chrome ignores the path in host permissions, so a Chrome Web Store listing will show a broad-access warning and needs this justification. The dialog's font and sheet are exposed to `https://*/*` with dynamic URLs. Tests: `test/connected-domains.test.js`, `test/manifest.test.js`. Not yet seen live on a connected domain |
| Taptop's paste (`pasteFromClipboard`, module 48511) reuses existing classes only when the clipboard's `verId` is this site's `VER_ID`; otherwise it copies every existing class as `<name>-2` and the layers use the copy, whose custom `line-height` is rebuilt as 0px. Its own copy writes `verId` and `designId`; Bridge packages carry neither (live, disposable site, 2026-11-27: a colleague's import produced `type-hero-2` with 0px; probe pastes confirmed both modes) | 0.2.1 adds this site's `verId`/`designId` to the clipboard before every paste (`sameSiteClipboard`), so the paste reuses the classes the class sync has just written. Test: `test/taptop-runtime-adapter.test.js` |
| With the same-site paste (`verId`), the paste reuses any class of the site with the same name: one from another Bridge project, one made by hand, or one of this project. Taptop classes belong to the whole site, while receipts are kept per page (`design` in the target key). Adopting such a class used to update only the properties in the file: an imported page's footer kept the dark `background` of a `.footer` another Bridge project owned, and taking that class over would have broken the other project's page (live, disposable site, 2026-11-27) | 0.2.1 reads which project each class belongs to from the receipts of every page of the same site (`siteClassOwners` in `src/lib/class-sync.js`) and decides per class: bound to this project → only updated; bound to another project → not touched, this package gets its own copy (`footer` → `footer-5`, renamed in layers, rules, Embeds and the receipt); bound to no project → adopted with every rule owned, so the merge removes what the file does not have (`adopt({ takeOver })`). An ownerless class is observed whole (all rules of `.name` and `.name:…`). Bindings this project made on other pages of the site join the page's receipt for the same stable keys (`siteProjectBindings`), so a page import uses the copy its UI kit import made instead of making another. A real import on the disposable site gave the page its own `footer-5`; a dry run on another page of that site reused `footer-5` and made no copy. A dry run of a page on a disposable site copied `footer` and `hero` and left the other project's classes untouched. Tests: `test/take-over.test.js` |
| A native Taptop control keeps one number with px, %, em, rem, vw or vh, or `auto`/`none`/`normal`; `line-height` only px; `font-weight` only 100–900/normal/bold. Packages from older Bridge builds wrote some other values as native rules (`border-radius: 20px 20px 0 0`, `font-weight: inherit`, `line-height: normal`), and the class sync stopped midway with «Не удалось обновить класс» after other classes had already changed (live, 2026-11-27) | 0.2.1 refuses such a package when the file is chosen, before anything changes (`PACKAGE_REBUILD_REQUIRED`, `staleRuleErrors` in `src/lib/layer-safety.js`), checking the pasted selector collections and the class-sync rules: «файл собран старой версией Bridge… Пересоберите». The rule mirrors `toTaptopRule` in Bridge's `system/lib/css-rules.js` (2026-11-27); when Bridge changes it, change both. Checked on 62 real packages: every build of 2026-11-26/27 passes, 25 older builds are caught. The invalid-file dialog also showed every specific reason as «файл экспорта повреждён» because it translated the reason twice; it now keeps the raw reason and translates it once. Tests: `test/import-safety.test.js`, `test/import-ui.test.js` |
| A custom attribute named `id` on a layer (`attr.id`, `data.id`) overrides the HTML id Taptop generates and breaks publication (reported by the Taptop developers, 2026-11-26; not reproduced live) | 0.2.1: the file check and the paste refuse it (`RESERVED_TAG_ATTRIBUTE`, `src/lib/layer-safety.js`); layer identities and ids inside SVG, Rich Text and Embed code are untouched. Tests: `test/import-safety.test.js` |

Live check of 0.2.1 loaded in Chrome, disposable site, 2026-11-26, through the adapter the extension injected: editor found (layer clipboard 48511); a package with `data.id` refused with no layer added; a synthetic page pasted after the version check, saved (style version 48 → 49) and still present after reload; a second tab one save behind was refused by the server-version check of that build (49 vs 50), which was then removed at the Taptop developers' request. Not exercised: the dialog's file drop with image upload and class sync, which the browser tooling cannot reach inside the closed shadow root.
